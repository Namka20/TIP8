### CI/CD: настройка GitHub Actions для сборки и проверки проекта

---

## 1. Краткое описание

В рамках работы был настроен CI pipeline с использованием **GitHub Actions**.

Pipeline автоматически выполняется при каждом `push` и `pull_request` и включает:

- запуск тестов (`go test`)
- сборку сервисов (`go build`)
- сборку Docker-образов
- (опционально) публикацию образов в registry (GHCR)

Таким образом обеспечивается базовая автоматизация проверки качества и сборки проекта.

---

## 2. Структура pipeline
Pipeline состоит из двух основных jobs:

Test job выполняет:

- checkout репозитория
- настройку Go
- загрузку зависимостей
- запуск тестов
- сборку сервисов

---

Docker job выполняет:

* подготовку тегов образов
* настройку Docker Buildx
* авторизацию в registry
* сборку образов
* push (только для push-событий)

---

## 3. Версионирование образов

Для Docker-образов используется следующая стратегия:

* `latest` — последняя версия
* `<short_sha>` — короткий hash коммита
Это позволяет однозначно определить, из какого коммита был собран образ.

---

## 4. Работа с секретами

В pipeline используются встроенные механизмы GitHub:

* `GITHUB_TOKEN` — для публикации образов в GHCR

Секреты:

* не хранятся в репозитории
* не прописываются в `.yml`
* передаются через GitHub Actions Secrets

Это обеспечивает безопасность доступа к registry.

---

## 5. Сборка Docker-образов

Сборка выполняется отдельно для двух сервисов:

* `auth`
* `tasks`


---

## 6. Условия выполнения

Pipeline запускается при:

* `push` в ветки `master` или `main`
* `pull_request`
* ручном запуске (`workflow_dispatch`)

## Ответы на контрольные вопросы
**1. Чем CI отличается от CD?**
CI (Continuous Integration) — автоматическая сборка и тестирование кода при каждом push'е в репозиторий. CD (Continuous Delivery/Deployment) — автоматическое развёртывание собранного артефакта на окружение (staging/production).

**2. Почему pipeline должен запускать тесты?**
Чтобы автоматически выявлять ошибки на ранних этапах, предотвращать попадание сломанного кода в основную ветку и обеспечивать уверенность в качестве перед деплоем.

**3. Зачем нужен автоматический build?**
Гарантирует, что код всегда находится в собираемом состоянии, создаёт воспроизводимые артефакты (бинарники, образы) и избавляет от проблемы "у меня собирается" на машине разработчика.

**4. Почему важно собирать Docker-образ в CI, а не только локально?**
Обеспечивает единообразие сборки в изолированном окружении, гарантирует воспроизводимость, проверяет, что Dockerfile корректен, и создаёт образы для всех окружений из одного источника.

**5. Что такое CI secrets?**
Переменные окружения, зашифрованные или защищённые в CI-системе (токены, пароли, SSH-ключи), которые подставляются во время выполнения pipeline, но не видны в коде или логах.

**6. Почему нельзя хранить токены и SSH-ключи в репозитории?**
Любой с доступом к репозиторию (включая сторонних разработчиков при утечке) сможет их украсть. Это приводит к компрометации инфраструктуры и сервисов.

**7. Для чего нужен тег Docker-образа?**
Идентифицирует версию образа (например, git commit SHA, номер сборки, версия приложения). Позволяет однозначно ссылаться на конкретный образ, откатываться и отслеживать изменения.

**8. Что делает job docker-build?**
Собирает Docker-образ из Dockerfile, тегирует его (обычно commit hash и latest) и пушит в container registry (Docker Hub, GitHub Container Registry и др.).

**9. Почему в multi-service проекте важен working-directory?**
Так как каждый сервис находится в своей поддиректории (`.gitlab-ci.yml`, `backend/`, `frontend/`), указание `working-directory` позволяет выполнять команды в правильном контексте без явных `cd` в каждом шаге.

**10. Какие риски возникают при полностью автоматическом деплое?**
Автоматический деплой на production может выкатить сломанную или небезопасную версию до обнаружения проблемы, требует надёжных тестов, мониторинга, автоматического отката и строгого контроля доступа к CI/CD.
